Reliability

Validation.

A generated sampler is only useful if it is correct. AI4BayesCode validates in two stages. Before any code is written it confirms that the parsed model matches the intended model. After, it checks that the sampler compiles, reads correctly, and recovers the right posterior.

No automated check catches every bug. Validation improves the reliability of generated samplers, and because AI4BayesCode runs inside a coding agent, you can continue to check the sampler after it is generated.

Stage 1

Pre-generation validation: get the model right.

Most errors start in the model. Before generating anything, AI4BayesCode makes the parsed model explicit and asks you to confirm it. This step is called user verification. In the coding agent, it always takes place and cannot be skipped. Nothing is generated until you confirm. Every check that comes later verifies the code against the parsed model, so pre-generation validation is the one point where an incorrectly parsed model can still be caught.

Prior completion.

Priors you already wrote are used exactly as you wrote them, and the system does not ask about them again. If your natural-language model description already gives every prior, the system asks no questions about priors and moves straight to the final confirmation in user verification, described below. For the priors that are missing it asks one parameter at a time, and it offers clear options. You can take a default weakly-informative prior, ask for a prior built from the published literature, fix the parameter to a known value, or supply your own. For the literature option the system searches the literature, shows you the sources it used, and offers a tighter version and a wider one, defaulting to the wider one. If you named a distribution but not its numbers, you can also leave those numbers adjustable so you can change them later without regenerating the code. Nothing is left implicit.

User verification.

You see the model twice. The moment you describe it, the system writes the model back as formulas and asks whether it parsed your model description correctly, before it asks you anything else. Once the priors are settled it shows the complete parsed model again for your final confirmation, in three views. The first is the model formulas, which are the likelihood and priors the system parsed. The second is a directed acyclic graph (DAG) of model dependencies, showing how each quantity produces the next. The third is a summary table of every parameter with its prior and the sampling block that will handle it. The table is where the block assignment is proposed, and you can ask for a different sampling block on any parameter right there. Whenever you ask for a change, all three views are redrawn, so you are always confirming something you can see. You can also ask to see the parsed model again at any point before generation starts. When something is ambiguous, such as two parameterizations of the same distribution, the system asks before continuing.

Papers work as input.

You can hand over a paper instead of writing a model description. The system reads the paper, writes back the parsed model, and asks you to confirm before anything is generated. Parsing a paper can introduce errors, so user verification matters even more here than it does for a model description you wrote yourself. If the paper defines several models, the system lists them first and you choose which ones to build, and each one becomes its own sampler.

Stage 2

Post-generation validation: check the sampler.

Once the sampler is written, the system runs a three-level pipeline, cheapest first. If a level fails, the AI agent revises the code from the accumulated feedback and validates it again. You set the maximum number of attempts before generation starts, and the default is five. When the only problem is that the chains have not converged yet or mix poorly, they are re-run five times longer first, and that longer run does not use up an attempt.

1 · Syntax validation

The generated C++ has to compile. The compiler performs this check. If the build fails, the agent revises the code and validates it again.

2 · Semantic validation

Semantic validation consists of twenty-six checks for bugs that compile and run but still give a wrong posterior: distribution parameterization, dimension mismatch, Jacobian handling, dependency consistency, update logic, gradient correctness, and more. Most of them are done by reading the generated code. A few go further and compile and run a small test program while the sampler is being generated, including the one that checks AI-written gradients against automatic differentiation. Two of them, readapt_NUTS() state-preservation and kernel-control conformance, cannot be settled by reading the code alone. The behavior of readapt_NUTS() and the freeze controls is confirmed in the runtime smoke test, which calls those methods directly.

3 · Runtime validation

The sampler is run on data simulated under the target model. The three runtime checks run in order, and a failure stops the ones after it. The first is a short smoke test of about ten iterations. It calls every method of the sampler at least once, and a single failed check fails the whole smoke test. It catches crashes, non-finite values, prediction that changes the chain state, and prediction that breaks once part of the model is held fixed. The second is the real run of two chains, each with 4000 burn-in iterations and 4000 posterior draws. R-hat and effective sample size (ESS) diagnostics are used to check whether the sampler converges. Every draw is kept, so the third check can reuse the same pair of chains. The third is a posterior predictive check, and its Bayesian p-values are used to test whether the sampler converged to the right posterior. PSIS-LOO is reported next to them as a diagnostic, and it never fails the sampler on its own.

The smoke test also checks the sampler the way you will use it. The sampler has to build from the data alone. Every other argument must have a default value, unless it is a modeling choice with no sensible default. Arguments passed by name, in any order, have to reach the right place, and a misspelled name has to stop with an error instead of being ignored. Every data input can be replaced from outside, and the new value has to remain in place after the next step.

The same standard applies to prediction. When you predict with new values for only some of the inputs, the sampler has to return every output that is still reachable in the prediction DAG. It must not return anything more, because an extra output means a missing input was filled in from the training data. When every draw is kept, prediction can also be set to use the current draw only, and the smoke test checks both forms. One last check applies only to models with differential equations. When the equations are linear and their coefficients do not change over time, the sampler has to use the library’s exact solution. A step-by-step numerical solver fails the check there, because its small numerical errors distort the posterior.

Some models are fitted with variational blocks instead of MCMC chains, in whole or in part. R-hat does not apply to those blocks, so runtime validation measures how close the fitted approximation is to the true posterior and grades it as pass, caution, or fail. When a model uses both kinds of block, both checks run and both have to pass.

Validation never evaluates a sampler by comparing it with a frequentist fit, because a maximum-likelihood estimate is not a posterior. Comparing it with another package or another sampler is discouraged as well. That package may use different priors, and then the comparison cannot show whether this sampler is correct.

Show the 26 semantic checks
  1. Distribution parameterization. Every distribution is annotated with its exact parameterization and mean.
  2. Sequential update. Vector Gibbs updates write each component back before the next one is drawn. Drawing them all at once is allowed only when the components do not depend on each other.
  3. Dead parameters. Every parameter has a block that samples it, and nothing is sampled and then left unused.
  4. Regression intercept / offset. The regression mean includes the intercept and any offset.
  5. Jacobian handling. Constrained NUTS parameters get their change-of-variable term from the library’s constraint transforms, never from an AI-written line in the model code.
  6. DAG consistency. The prediction DAG matches how the code computes things, and every value the prediction step reads can be reached from that DAG.
  7. Dependency declaration. Each block declares the conditioning quantities it reads.
  8. Rcpp API correctness. The R interface is used correctly, covering matrix layout, list handling, and how errors are raised. Two of those rules exist because the same file is also compiled for Python, so one wrapper serves both languages.
  9. Numerical stability. Log-sum-exp, clamping, and overflow guards are in place.
  10. State mutation in predict_at(). Posterior prediction does not alter the chain’s state.
  11. Joint NUTS block extra audit. Extra checks run when a joint NUTS block is used.
  12. Gradient verification via autodiff. AI-written gradients are checked against automatic differentiation.
  13. RNG separation. Sampling and prediction draw from separate random streams.
  14. Bijection-consistency AD check. Custom trans-dimensional maps are probed at a set of test points. A round trip through each map has to return the starting value, the Jacobian has to stay non-singular, and the forward and reverse steps have to be consistent with each other.
  15. Library parity test. Gibbs and other specialized blocks are tested by drawing many samples and confirming the mean and variance match the distribution the block is supposed to be drawing from.
  16. Inline Gibbs-exception justification. Every closed-form Gibbs step has a short comment, in plain words, on why that step is exact for this model. The comment is written for whoever reads the file, so it never cites check numbers or file paths.
  17. No AI-written Gibbs outside whitelist. AI-written Gibbs updates are used only in whitelisted cases.
  18. Dense metric justification + pilot scaling. A dense NUTS metric is justified and pilot-scaled.
  19. Vectorized gradient computation. Gradients use BLAS-friendly matrix operations.
  20. No per-step warmup in NUTS blocks. The sampler never re-warms inside a recording step.
  21. VI block contract conformance. Variational blocks conform to the required interface.
  22. VI optimizer is RAABBVI. Variational blocks use the RAABBVI optimizer.
  23. readapt_NUTS() state-preservation. Every sampler with a NUTS block provides re-tuning. Re-tuning leaves the chain state unchanged and draws from its own random stream.
  24. Joint-NUTS pathology pre-flight. Funnel models are written in the non-centered form, because the centered form leads to poor mixing under NUTS. Each parameter’s constraint matches the support declared in the model, and the joint density reads every parameter that the joint NUTS block declares.
  25. Trans-dimensional / Dirac-spike RJMCMC. Models where a coefficient can be exactly zero, and models where the number of parameters can change, are sampled with reversible jump instead of a fixed-size sampler. One way of getting this wrong leaves every runtime check passing while the exact zeros disappear, which is why it is caught by reading the code.
  26. Kernel-control conformance. The controls that hold part of a model fixed while the rest is still sampled are present and behave safely. Freezing a name that does not exist, or a block that cannot be frozen, raises an error, and you are warned if you re-freeze something already frozen or leave a stale derived value behind.

These twenty-six checks come with the library itself. A contributed block includes its own checks as well, and those run in addition to these whenever your sampler uses that block.

The two stages complement each other: the first checks that the intended model is being fit, and the second checks that the sampler fits it correctly.

Even so, no validation catches every bug. That is why AI4BayesCode runs inside a coding agent: when the sampler is generated, the conversation does not end. You can keep going and ask the agent to probe edge cases, read through the code with you, and search for anything the automated checks missed.
